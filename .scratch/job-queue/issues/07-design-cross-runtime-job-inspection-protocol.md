# Design Cross-Runtime Job Inspection Protocol

Category: enhancement
Status: ready-for-agent

## Parent

.scratch/job-queue/PRD.md

## Agent Brief

**Category:** enhancement
**Summary:** Design and implement one safe Job inspection contract across Dev,
local Container, and Hosted Capsule runtime paths.

**Current behavior:**
Capsule server code can get and filter actor-scoped Job state. Sporades has no
shared operator inspection action or schema capable of carrying all safe Job
state consistently through the CLI, runtime, Container, Host helper, and Hosted
protocols.

**Desired behavior:**
Administrators and AFK agents can inspect all Jobs in a Capsule through
deterministic JSON regardless of runtime location. All transports use one
bounded, redacted runtime-owned action and preserve Capsule isolation. The first
slice does not add actor scoping, filters, cursors, or pagination.

All three commands are JSON-only and always emit Sporades' standard structured
JSON envelope. V1 has no human renderer and does not require a `--json` flag.
Successful inspection returns `data.capsule.name` and `data.jobs`; it does not
add a session-location field, redundant count, or speculative schema version.

Each Job exposes operational state: Job ID, handler, status, actor mode,
`enqueuedBy`, attempt count and bounded attempt history, retry policy, lifecycle
timestamps, whether an idempotency key is present, and bounded result or failure
metadata already classified safe by the runtime. It omits input payloads and
idempotency-key values.

Every Job uses one stable JSON shape with explicit nullable fields:
`id`, `handler`, `status`, `enqueuedBy`, `actor`, `attempts`, `retry`,
`idempotencyKeyPresent`, `availableAt`, `createdAt`, `startedAt`, `completedAt`,
`failedAt`, `cancelRequestedAt`, `leaseExpiresAt`, `attemptHistory`, `result`,
and `failure`. Current-user actors include `userId`; Privileged server role
actors expose only their mode.

**Key interfaces:**

- Job inspection action/schema — returns all bounded safe Job states plus
  structured failures.
- `jobs.inspect` — the shared internal runtime and Host-helper action identifier;
  it accepts no filter or pagination arguments.
- Dev inspection transport — uses Dev-session metadata to verify the recorded
  process is active and invokes the shared read-only inspection function against
  the Dev session Runtime directory.
- Container inspection transport — invokes the shared action inside the bound
  Container through `docker exec`.
- Hosted inspection transport — asks the Host helper to invoke the shared action
  inside the Hosted Capsule through `docker exec`.
- Generated server Bundle action mode — `node <server.mjs> --sporades-action
  jobs.inspect` detects the internal action before normal HTTP, WebSocket, or
  lifecycle startup and before Capsule-module evaluation, emits one JSON
  envelope, and exits.
- Database adapter — the action reads runtime-owned Job state through the
  Capsule's configured SQLite, libSQL, or Postgres adapter rather than opening a
  SQLite file directly.
- CLI JSON renderer — exposes the safe action result without adding an API
  route.
- `sporades jobs` — inspects the active Dev session.
- `sporades deploy jobs` — inspects the bound local Container session.
- `sporades host jobs --host <alias> --subname <name>` — inspects one Hosted
  Capsule through its Host server.

**Acceptance criteria:**

- [ ] A documented runtime-owned action/schema returns bounded safe state for all Jobs in one Capsule.
- [ ] The internal action identifier is `jobs.inspect`; its request carries only transport-required target identity and no inspection options.
- [ ] Dev, local Container, and Hosted Capsule paths return the same JSON envelope and structured error behavior.
- [ ] All three commands are JSON-only, always emit the standard Sporades JSON envelope, and neither require nor offer a separate `--json` mode in v1.
- [ ] Success has the shape `{ ok: true, data: { capsule: { name }, jobs }, error: null }` across all three commands.
- [ ] An empty queue succeeds with `jobs: []`; callers derive the count from `jobs.length`.
- [ ] V1 adds no session-location field, redundant count, or explicit schema-version field.
- [ ] If any stored Job cannot be decoded, the whole action fails with `JOB_INSPECTION_INVALID_STATE`, identifying only the Job ID and malformed field without returning a partial array or corrupt raw value.
- [ ] A missing runtime-owned Job store/table succeeds with `jobs: []`; inspection does not create or migrate storage.
- [ ] The first slice has no actor-scoped filtering, user-supplied filters, cursor, or pagination; callers may filter the JSON output themselves.
- [ ] Jobs are ordered by `createdAt DESC`, then Job ID descending, so the newest work appears first and repeated inspection is stable when queue state has not changed.
- [ ] The shared inspection function reads all Jobs in one read transaction/snapshot so the returned array represents one coherent database view.
- [ ] Inspection reads through the Capsule's configured Database adapter and works with SQLite, libSQL, and Postgres runtime persistence.
- [ ] Dev reproduces the active session's runtime configuration for the one-shot Bundle; Container invocations inherit the target Container's configured environment.
- [ ] Inspection never exposes payloads by default, raw runtime tables, Server env values, tokens, cookies, browser credentials, or raw stack traces.
- [ ] Each Job includes its ID, handler, status, actor mode, `enqueuedBy`, attempts, bounded attempt history, retry policy, lifecycle timestamps, idempotency-key presence, and bounded safe result or failure metadata.
- [ ] Input payloads and idempotency-key values are never returned by the v1 inspection action.
- [ ] Every Job contains the same fields with absent lifecycle values, result, and failure represented as `null` rather than omitted.
- [ ] `actor` is `{ mode: "current-user", userId }` for captured-user Jobs and `{ mode: "privileged-server-role" }` for Privileged Jobs.
- [ ] Access relies on the administrator's existing ability to operate the Dev session, Container session, or Host server and preserves Capsule isolation.
- [ ] Local Dev inspection does not pass or validate the HTTP inspection token; filesystem access is the authority and Dev-session metadata only verifies and locates the active target.
- [ ] Inspection emits no Privileged audit event because it is a bounded read-only operator action and does not run as the Privileged server role.
- [ ] The action is an internal CLI/runtime operation, not an HTTP or Capsule API route.
- [ ] All three transports call one shared read-only Job inspection function rather than querying Job tables through generic SQL.
- [ ] Dev invokes the function against the Dev session Runtime directory; local Container and Hosted Capsule inspection invoke it inside the target Container through `docker exec`.
- [ ] Dev runs `node .sporades/build/server.mjs --sporades-action jobs.inspect`; Container paths run `node /app/server.mjs --sporades-action jobs.inspect` through `docker exec`.
- [ ] The generated Bundle detects this internal action before importing or evaluating Capsule code and before migrations, recovery, workers, lifecycle hooks, runtime-start logs, HTTP, or WebSocket work.
- [ ] Inspection loads only Sporades-owned configuration, required Database adapter credentials, and the read-only inspection function, writes exactly one JSON envelope, and exits.
- [ ] No Capsule-authored top-level code or handler executes during Job inspection.
- [ ] `--sporades-action` remains a Sporades-owned internal CLI/runtime contract rather than a Capsule authoring API.
- [ ] `sporades jobs`, `sporades deploy jobs`, and `sporades host jobs --host <alias> --subname <name>` target Dev, local Container, and Hosted Capsule sessions respectively without automatic target detection.
- [ ] Dev inspection requires an active Dev session; local and Hosted inspection require the target Container to be running.
- [ ] Missing, stopped, or unreachable targets return structured errors with the appropriate start or restart command.
- [ ] Inactive Dev sessions, missing bindings, stopped Containers, unreachable Host servers, and stopped Hosted Capsules reuse their existing structured CLI errors rather than adding Job-specific variants.
- [ ] A Host server whose installed Sporades CLI/Host helper does not support the Job inspection action returns `HOST_HELPER_UPGRADE_REQUIRED` with a hint to run `sporades host upgrade`.
- [ ] Focused tests exercise the real one-shot generated Bundle and a temporary Dev session, plus existing fake Docker and fake SSH/Host-helper seams for local and Hosted Containers.
- [ ] Adapter tests cover SQLite, libSQL, and Postgres using the repository's existing conditional external-service setup.
- [ ] Tests cover deterministic JSON, snapshot consistency, bounded disclosure, missing storage, malformed stored state, unavailable targets, Host-helper upgrade guidance, and generated Bundle/Host-helper parity.
- [ ] The standard suite requires no live Host server; a later Hosted Capsule smoke run is useful but does not gate Issue 07 completion.

**Out of scope:**

- Changing Job execution, retry, lease, cancellation, or actor semantics.
- Recurring Job scheduling.
- Generic raw SQL access to runtime-owned Job tables.
- Actor-scoped operator inspection, filters, cursor pagination, and pagination.
- An HTTP, Custom endpoint, or other Capsule API route for Job inspection.
- Human-oriented Job output or a second rendering mode.
- A generic runtime-table inspection command.
- A SQLite-specific inspection implementation that bypasses the Database adapter.
- A second inspector executable or Base-image artifact.
- Reusing normal runtime bootstrap when it would evaluate Capsule code or perform writes.
- Offline Job inspection, direct volume mounting, or ephemeral inspection Containers.
- Privileged server role execution or Privileged audit events for inspection reads.
- Fallback Hosted inspection through SSH-side SQL, direct file reads, or protocol guessing when the Host helper is too old.
- Partial-success inspection that omits or returns raw malformed Job state.
- New Job-specific error codes for target/session failures already represented by existing CLI contracts.
