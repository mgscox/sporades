## Question

What runtime-owned records, adapter methods, indexes, transaction boundaries, migrations, limits, cleanup rules, and cross-engine conformance obligations preserve user ownership and Access-key lifecycle invariants across rollback, restart, concurrency, SQLite, libSQL, and PostgreSQL?

## Comments

### Resolution — 2026-08-20

The Auth runtime owns one stable Access-key lifecycle record per key. Its engine-neutral fields are `id`, `ownerUserId`, immutable `name`, nullable `reservedName`, canonical `grantsJson`, `secretVersion`, nullable `selector`, nullable `verifierDigest`, `lifecycleRevision`, `createdAt`, optional immutable `expiresAt`, optional `rotatedAt`, optional `revokedAt`, optional runtime-defined `revocationCause`, and optional approximate `lastUsedAt`. Text is the portable stored representation; the v1 verifier digest is exactly 64 lowercase hexadecimal characters.

The key ID is the attribution identity and survives rotation. V1 stores a domain-separated SHA-256 digest rather than introducing a Host-managed HMAC pepper. Each key record contains exactly one current selector and digest, with no secret-version history or rotation overlap. Rotation atomically replaces both fields, records `rotatedAt`, increments `lifecycleRevision`, and discloses the new complete token only after commit. It compares and swaps against the caller-observed lifecycle revision, so only one contender using a revision succeeds. Revocation is terminal and idempotent: it clears `selector`, `verifierDigest`, and `reservedName`, records its time and one of the runtime-owned causes `owner`, `operator`, `password-reset`, `owner-unlinked`, or `owner-deleted`, and increments the lifecycle revision when it performs the transition.

The key table has a primary key on `id`, a unique credential index on `(secretVersion, selector)`, a unique current-name constraint on `(ownerUserId, reservedName)`, and an owner-listing index on `(ownerUserId, createdAt, id)`. SQL null semantics permit many revoked rows after their selector and name reservation are cleared. Names are trimmed, non-empty, case-sensitive, at most 128 Unicode code points, and unique only among one owner's current keys. Active and expired keys keep `reservedName = name`; revoked keys retain immutable `name` for attribution while releasing the reservation.

A second runtime-owned Access-key owner ledger uses `ownerUserId` as its primary key and stores `currentCount`, `totalCount`, and `operationRevision`. V1 permits at most 100 current keys and 1,000 retained records per owner. An issuance locks the ledger by conditionally advancing its revision, verifies current linked/non-guest owner eligibility, reserves both counters, and inserts the key in one Auth transaction. Failure rolls back the counters and record together. Every lifecycle mutation and owner-security transition touches the same ledger first, giving issuance, rotation, revocation, account-recovery password reset, loss of linked status, and owner deletion a portable serialization point without dialect-specific row-lock syntax. Revocation decrements `currentCount`; deletion of a revoked historical record decrements `totalCount`. Hard deletion refuses active and expired-current records.

One key may contain at most 128 grant expressions, each no more than 256 UTF-8 bytes, with canonical JSON no larger than 32 KiB. The Capsule definition may declare at most 1,024 scopes, each no more than 256 UTF-8 bytes, so every declaration remains exactly grantable and wildcard matching has bounded input. Grant expressions are validated and canonically sorted before persistence; no database engine performs scope matching.

The Database adapter seam remains engine-agnostic and lifecycle-specific rather than exposing generic table CRUD. Its shared method set covers issuance, indexed credential lookup with the owning user, owner-scoped metadata reads and listing, compare-and-swap rotation, idempotent direct revocation, bulk owner revocation, revoked-history deletion, and monotonic usage recording. These methods hide owner-ledger choreography, conditional statements, and stored-row normalization. Auth runtime workflows own the surrounding `withTransaction` calls and secret generation/disclosure; no adapter opens a nested transaction.

Credential admission performs one indexed statement joining the key to its owning user. That statement snapshots the stored digest, lifecycle state, immutable grants, and current owner eligibility. Digest comparison and scope checks finish against the snapshot without holding a transaction through Capsule work. A lifecycle change committed before the lookup begins is observed; a later commit affects subsequent admissions, not work whose check already passed.

Password-reset confirmation extends its existing Auth transaction: consuming the Reset code, changing the password, deleting sibling Reset codes, deleting Sessions, and bulk-revoking current Access keys commit or roll back together. Any future loss-of-linked-status or owner-deletion workflow likewise shares one transaction with bulk key revocation. The Access-key owner reference is logical rather than a cascading foreign key, so owner deletion can retain historical attribution after revocation.

`lastUsedAt` records successful Access-key admission only. It is monotonic, best-effort telemetry outside Capsule work transactions, coalesced to at most one write per key per hour per runtime process. A failed or lost telemetry write cannot fail admitted work; a restart may cause one additional write.

Failed-admission throttling is bounded process state rather than attacker-driven database storage. The source bucket permits 30 failures per minute; the process-keyed selector-fingerprint bucket permits 10 failures per five minutes. Each LRU holds at most 10,000 live entries, idle entries expire after 15 minutes, and successful authentication clears its selector bucket. Restart clears both limiters. Host configuration may override thresholds and capacities and may supply distributed edge controls; Capsule code cannot change them. Successful-request quotas remain Capsule or Host policy rather than Access-key authentication.

`ensureAuthStorage()` always creates the Access-key and owner-ledger tables and indexes, even when the current Capsule declares no scopes or wraps no endpoint. The migration is additive and idempotent, requires no legacy backfill, preserves every existing auth row, and follows the existing ordered bootstrap outside a transaction. Existing databases therefore restart with empty Access-key storage; future Capsule-definition changes do not change the storage shape.

The auth-storage conformance surface must exercise every new adapter method without branching on engine or exempting an Access-key method from method coverage. SQLite, service-backed libSQL, and PostgreSQL proof covers bootstrap idempotence, stored-row parity, unique current names and reuse after revocation, indexed selector lookup, quota enforcement and rollback, one-winner same-name concurrent issuance and same-revision rotation, issue-versus-owner-transition serialization, atomic password-reset revocation, old-secret failure after rotation, scrubbed-secret failure after revocation, monotonic/coalesced telemetry, explicit historical deletion, and persistence across close/reopen. The emitted-PostgreSQL quoting audit and generated runtime parity tests must include the new tables, indexes, and shared methods. An engine-specific behavioural override is a conformance failure rather than an accepted adapter difference.
