# 08 — Verify real providers on a Hosted Capsule

**What to build:** Prove the completed multi-provider flow against real Google, Microsoft, Apple, and Facebook registrations on one HTTPS Hosted Capsule. Capture reproducible operator evidence that each provider completes a full-page sign-in, produces the expected Sporades auth state, and preserves Anonymous-session continuity.

**Blocked by:** 07 — Contract Google-specific auth and prove provider coexistence.

**Status:** external-blocked

- [ ] A dedicated acceptance Capsule is registered on an HTTPS Hosted domain and configured with secret-safe credentials for all four OAuth providers.
- [ ] Each provider console contains the exact Hosted Capsule callback URI generated by Sporades, with provider-specific application mode, tenant, website, permission, and key requirements satisfied.
- [ ] Google, Microsoft, Apple, and Facebook each complete a real full-page browser sign-in from a fresh Anonymous session and return to the initiating page.
- [ ] Each successful flow records safe evidence of provider name, stable Sporades user ID continuity, authenticated state, display data available from that provider, and restored return location.
- [ ] A second sign-in with each same provider identity resolves the same Sporades user rather than registering another account.
- [ ] At least one cross-provider link on an already authenticated Sporades user proves that multiple Provider identities can belong to one Linked account without email-based automatic merging.
- [ ] Cancellation and one deliberate provider misconfiguration produce the documented structured recovery path without exposing credentials or tokens.
- [ ] Apple is verified through its real HTTPS form-post callback, including a repeat sign-in where first-authorization name data is absent.
- [ ] Container and Hosted Capsule status, logs, callback responses, browser behavior, and post-sign-in Capsule behavior are checked rather than relying only on provider-console success.
- [ ] Acceptance evidence records provider-console prerequisites and verification dates without copying secrets, raw tokens, private keys, or personal profile data into the repository.
- [ ] Temporary acceptance resources remain available unless the maintainer explicitly requests teardown.
