## Problem Statement

A recently fixed CPU runaway in the `saas-tickets` Capsule exposed a wider operational gap: Sporades operators need continuous resource history and timely alerts, plus enough application telemetry to explain slow or failing work. Existing health checks, structured logs and on-demand Docker statistics do not provide that complete view.

Operators need to inspect API route latency, errors and request traces alongside container CPU, process memory, JavaScript heap, garbage collection and event-loop pressure. Application telemetry alone cannot report reliably when its event loop is blocked. The monitoring system must retain visibility outside the Capsule process.

Any Sporades user must be able to host the monitoring stack using Docker Compose. Its VM may differ from the Host server running Capsules, so destinations, credentials and collection must be configured and maintained through Sporades rather than hard-coded into individual apps. An operator-owned `.env` is the agreed source for Compose configuration and secrets.

## Solution

Add automatic OpenTelemetry instrumentation to the Sporades runtime, with continuous host/container collection and independent application probes. Connecting a Host to monitoring enables all its existing and newly deployed Capsules by default, with explicit per-Capsule opt-out. Local Dev and Container sessions remain opt-in. Provide a portable, versioned Docker Compose monitoring distribution with persistent metrics and traces, dashboards and actionable alerts.

Introduce a Monitoring server and Telemetry profiles as concepts distinct from the existing Host server and Host profile. One Monitoring server can serve multiple Host servers belonging to one operator. Host-side agents send telemetry outbound over authenticated HTTPS; Capsules do not require inbound public metrics ports or access to Docker. Monitoring must operate after the configuring workstation disconnects.

Sporades supplies stack generation, profile registration, Host binding, lifecycle reconciliation and end-to-end diagnostics. Users configure the stack through its `.env`, select the connection through Sporades, and receive automatic platform telemetry without importing OpenTelemetry in app code. Ordinary Capsule operation remains available when monitoring is disabled or temporarily unreachable.

## User Stories

1. As a Capsule operator, I want sustained CPU saturation to raise an alert, so that I can respond before the Capsule becomes unavailable.
2. As a Capsule operator, I want monitoring outside the application process, so that a blocked event loop cannot hide its own failure.
3. As a Capsule operator, I want CPU cores consumed, quota saturation and host utilization shown separately, so that Docker CPU percentages are interpreted correctly.
4. As a Capsule operator, I want container memory usage, limits, OOM events and restart history, so that I can recognize resource exhaustion.
5. As a Capsule developer, I want process RSS, heap, external memory and ArrayBuffer measurements, so that I can distinguish forms of memory growth.
6. As a Capsule developer, I want GC and event-loop measurements, so that I can relate runtime pressure to slow requests.
7. As a Capsule developer, I want automatic HTTP request traces, so that app code does not need manual instrumentation for standard routes.
8. As a Capsule developer, I want per-route throughput, latency distributions, failures and in-flight counts, so that I can identify regressions quantitatively.
9. As a Capsule developer, I want database and outbound-call spans, so that I can distinguish application work from dependency delays.
10. As a Capsule developer, I want file and authentication operation spans, so that runtime overhead is visible without exposing sensitive contents.
11. As a Capsule developer, I want WebSocket query and mutation operation telemetry, so that work outside ordinary HTTP requests is represented.
12. As a Capsule developer, I want job queue age, depth, execution traces and retry outcomes, so that background work can be investigated independently of API traffic.
13. As a Capsule operator, I want trace and request identities in existing logs, so that I can connect an observed failure to its detailed events.
14. As a Capsule operator, I want deployment and restart context on dashboards, so that changes can be correlated with regressions.
15. As a Sporades user, I want a versioned Docker Compose monitoring package, so that I can self-host the full stack on infrastructure I choose.
16. As a Sporades user, I want the monitoring stack to run on a separate VM from Capsule hosting, so that its placement matches my infrastructure and failure boundaries.
17. As a small-installation operator, I want the same stack to support a shared VM, so that I can start with fewer machines.
18. As a fleet operator, I want one Monitoring server to receive data from multiple Host servers, so that I can inspect the fleet centrally.
19. As a stack operator, I want a documented `.env` for settings and secrets, so that installation uses familiar Compose conventions.
20. As a stack operator, I want an example environment file without working credentials, so that I can configure the required values safely.
21. As a stack operator, I want initialization and upgrades to preserve my existing `.env` and overrides, so that my configuration and credentials are not silently replaced.
22. As a stack operator, I want persistent storage and documented backup, restore and upgrade procedures, so that telemetry history survives maintenance.
23. As a stack operator, I want published prerequisites and supported architectures, so that installation failures are explicit and actionable.
24. As a Host operator, I want a named Telemetry profile independent of my Host profile, so that the monitoring destination can be changed without moving Capsules.
25. As a Host operator, I want one shared collection and relay installation per Host, so that every Capsule does not need a duplicate monitoring stack.
26. As a Host operator, I want telemetry to use outbound authenticated connections, so that I do not need remote Docker access or inbound scrape ports on Capsule Hosts.
27. As a Host operator, I want monitoring configuration to survive workstation disconnection and Host restart, so that collection is a durable Host responsibility.
28. As a Host operator, I want start, restart, push and rollback to honor the saved monitoring policy, so that lifecycle commands remain consistent.
29. As a Host operator, I want destination and enablement policy under operator control, so that application configuration cannot redirect telemetry arbitrarily.
30. As a developer, I want explicit monitoring selection for Dev and local Container sessions, so that unrelated local projects do not silently export data.
31. As a Host operator, I want independently rotatable and revocable ingestion credentials, so that one sender can be removed without disrupting the fleet.
32. As a Host operator, I want diagnostic checks from the actual sender through stored telemetry, so that a successful laptop connection is not mistaken for a working deployment.
33. As a stack operator, I want durable expected-target inventory, so that a disappeared Host cannot remove its own missing-data alert.
34. As a fleet operator, I want registration, deployment, start, stop, deletion and address changes automatically synchronized with monitoring, so that coverage and alerts do not depend on manual inventory updates.
35. As a Capsule operator, I want useful notifications and recovery messages with dashboard links, so that alerts support action rather than just noise.
36. As a Capsule operator, I want public application probes and protected local readiness checks, so that both routing failures and runtime readiness failures can be distinguished.
37. As a Capsule operator, I want bounded telemetry buffering and retries, so that a monitoring outage cannot cause an application outage or memory runaway.
38. As a stack operator, I want telemetry loss and pipeline capacity visible, so that missing measurements are not interpreted as healthy zero activity.
39. As a Capsule operator, I want metrics independent of trace sampling, so that changing trace retention does not distort request counts or latency distributions.
40. As a stack operator, I want configurable sampling, retention and disk budgets, so that the installation remains affordable and bounded.
41. As a Capsule owner, I want credentials, payloads and private identifiers excluded from default exports, so that monitoring does not become a secondary data leak.
42. As a Capsule developer, I want concurrent request contexts isolated, so that traces and logs identify the correct operation.
43. As a Capsule developer, I want disabled monitoring to leave normal runtime behavior unchanged, so that adopting telemetry is optional and reversible.
44. As a release maintainer, I want telemetry tested in the installed CLI and generated base-image Bundle, so that source-only tests cannot conceal deployment failures.
45. As a release maintainer, I want fault and overhead acceptance tests before broad rollout, so that the monitoring feature has demonstrated operational value and acceptable cost.
46. As a Host operator, I want to disable exports or remove agents without deleting Capsule data or retained history, so that rollback is controlled.
47. As a Host operator, I want connecting a Host to enable monitoring for its existing and future Capsules by default, so that monitoring coverage does not require a separate opt-in for each deployment.
48. As a Host operator, I want an explicit per-Capsule opt-out, so that exceptions do not disable monitoring for the rest of the Host.
49. As a stack operator, I want a simple monitoring health endpoint, so that I can check readiness without a required watchdog service.
50. As a Host operator, I want lifecycle inventory to synchronize automatically after a monitoring outage, so that deployments remain available and monitoring eventually catches up.

## Implementation Decisions

1. **Domain boundaries.** A Monitoring server stores and presents observability data. A Host server runs Hosted Capsules and owns their lifecycle. A Telemetry profile describes a monitoring connection, while a Host profile retains its current meaning. Document the new terms in the domain glossary. The first release serves one operator/trust domain; service labels are not tenant-isolation mechanisms.

2. **Default stack.** Ship pinned OpenTelemetry Collector contrib, Prometheus, Grafana, Jaeger v2 with persistent Badger storage, Alertmanager and Blackbox exporter, with authenticated TLS ingress. Prometheus owns alert evaluation; Alertmanager owns grouping, silencing and notification delivery. Jaeger is the modest-volume, single-node trace store. Do not deploy a second trace backend in the default package. OTLP keeps the runtime independent of that storage choice; capacity must be demonstrated for the pilot rather than assumed.

3. **Portable distribution.** Publish a versioned Compose release asset and include stack-generation assets in the installed Sporades package. Provision data sources, dashboards, rules, persistent storage and health checks. Support normal Docker Compose operation without requiring the Monitoring server to be a registered Host server. Document prerequisites, image architecture support, measured capacity, backup/restore and upgrade/rollback. Stack generation creates a reviewable directory; it does not provision a VM or silently launch services.

4. **Compose environment and secrets.** Assume an operator-owned `.env` is available beside the Compose definition and may hold all needed secrets, including ingestion, dashboard and notification credentials. Provide an example with placeholders and non-secret defaults, and exclude the real file from version control. Preserve existing values and unknown operator additions during regeneration; report missing keys without their values. Never implicitly rotate or overwrite secrets. For fresh setup, generate only missing stack-owned secrets; external credentials are supplied by the operator. Use restrictive permissions, explicit per-service environment selection and protected generated files where components require them. Separate Compose secret management is optional. Preserve overrides and include private environment-file backups in restore instructions. Never emit resolved secret-bearing Compose configuration in diagnostics.

5. **Separate-VM transport.** Install one shared Host relay and an isolated Docker/host collection agent per monitored Host. Runtime telemetry enters the unprivileged relay over an explicitly configured private address/network. Host telemetry is forwarded outbound using authenticated OTLP/HTTP over HTTPS to the Monitoring server. The central gateway presents metrics to Prometheus inside the Compose network and exports traces to Jaeger. Use one ingestion path per signal family. Do not assume container loopback reaches the Host or remote VM.

6. **Collection authority.** The Docker-accessing collector must be export-only without app-facing OTLP ingress, or use a verified constrained API proxy. Do not mount the Docker socket in Capsules. Read-only mounting alone does not constrain Docker API authority. Host metrics must refer to the intended host, not accidentally the collector container; distinguish Docker Desktop's Linux VM from physical-host measurements. Pin the alpha Docker stats receiver and validate its actual cgroup-dependent metric set. Obtain missing OOM/restart/lifecycle information through verified inspect/event collection.

7. **Monitoring connection contract.** A versioned Telemetry profile includes its name, OTLP/HTTP base URL, dashboard URL, protocol and TLS trust/credential references. Exportable descriptors contain no credentials. Supply secrets separately through protected server configuration. Support supplied certificates/private CAs or an existing TLS proxy, without mandatory public DNS or a specific VPN. Remote mode requires verified TLS; an explicit loopback-only development mode is allowed. Storage, scrape and raw backend services remain internal by default.

8. **Sporades operator surface.** Add operations to generate/validate a stack, register a Telemetry profile, bind/reconcile/check monitoring for a Host, choose a profile for a local session, automatically synchronize expected-target inventory with manual export/import for recovery, rotate/revoke credentials, and disable/uninstall monitoring. Match current human and structured CLI conventions, including `{ ok, data, error }`. Host configuration is resolved and persisted on the Host through its existing authenticated helper and registry ownership; runtime execution must not depend on a workstation-local alias.

9. **Configuration precedence and lifecycle.** CLI processing validates policy and injects runtime configuration using existing seams. Connecting a Host enables monitoring for every existing and newly deployed Capsule on that Host by default. Hosted Capsules inherit its operator-approved destination and enablement constraints, with explicit per-Capsule opt-out; project policy selects permitted signals, sampling and collection interval but cannot redirect exports or override an operator disable. Existing Capsules that require a controlled restart are reported as pending until monitoring is actually active; configuring a Host must not falsely report immediate coverage. Local sessions resolve an explicit session profile, then an operator project binding, then no export; there is no implicit machine-wide export destination. Apply bindings through start, restart, push and rollback, reporting any required controlled restart. Keep stack `.env` independent from Capsule Sealed Server env; do not add implicit plaintext imports or alter Host key ownership and retained-release recovery.

10. **Credential lifecycle.** Issue revocable ingestion credentials per Host/workstation. Central credentials live at the Host relay rather than inside every Capsule where possible. Any local Capsule connection material is scoped to its relay. Ingestion does not grant dashboard administration or general query access. Rotation/revocation must reload predictably and be verifiable without revealing secrets. Reconfiguration cannot widen browser, ACL, File or Privileged authority.

11. **Runtime module.** A narrow internal telemetry module owns providers, async context, instruments, filtering, batching and bounded shutdown. Instrument default platform signals without app imports or a public instrumentation/plugin API. Integrate through existing HTTP/operation dispatch, log-envelope and lifecycle seams. Prefer explicit runtime-owned spans over broad monkey-patching. Selective dependency instrumentation must be proven against the actual generated ESM Bundle and must not duplicate server spans.

12. **Bundle invariants.** Preserve the same bundled execution contract across Dev, Container and Hosted modes. Dependencies must be inlined so a deployed Bundle requires no package resolution, download or install step. Keep the Host helper's opaque-Bundle contract and ordinary module-graph compilation; do not restore superseded function-registration machinery. Provider initialization precedes instrumented work; Dev restarts dispose timers/providers. One-shot inspection actions must retain their current behavior and not inadvertently evaluate Capsule code or initialize background telemetry workers.

13. **HTTP traces and metrics.** Create one SERVER span per HTTP request and independent request-count, duration-histogram, failure and in-flight metrics. Capture method, stable route identity, status, bounded outcome and duration. Cover early rejection, malformed request targets, auth, file and custom endpoints, 404s, errors translated into responses, aborts and streams. End once on completion or premature close. Use declared custom endpoint paths and explicit built-in templates; do not implement a new router or use raw paths/query strings as route labels. Keep unknown routes in one bounded fallback category.

14. **Operation tracing.** Add child spans for meaningful handler, auth, file, database and outbound HTTP work. Database metadata is bounded engine/operation/table information, not SQL parameters or payloads. Preserve internal adapter boundaries across SQLite and PostgreSQL and preserve authorization, rollback, concurrency and retry behavior. Outbound context propagation is restricted to approved destinations.

15. **WebSocket and job telemetry.** Represent logical WebSocket operations individually, with active connections and operation count/duration/errors; do not hold one trace for the lifetime of a socket. Expose queue depth, oldest pending age, job duration, retries and failures. Job execution has its own span and may link to validated enqueue context; do not retain an open span across queue delays or persist arbitrary baggage. Instrument existing durable lifecycle boundaries without changing execution guarantees.

16. **Memory and runtime measurements.** Periodically collect process CPU, RSS, V8 heap used/allocated/limit, external memory, ArrayBuffers, uptime, GC and event-loop delay/utilization, using APIs verified on supported Node versions. Keep process, container and host measurements separate. ArrayBuffers are already included in external memory. Do not measure or advertise per-request allocated memory through before/after heap deltas; concurrency and GC invalidate that attribution. Ordinary traces do not replace CPU or heap profiles.

17. **Infrastructure measurements.** Collect CPU time/cores, configured quota saturation, throttling, memory/limit, network/block I/O, PIDs, host CPU/load, available memory, disk/inodes and lifecycle evidence. Docker 100% generally represents one logical CPU; dashboards must not equate it with whole-host saturation. Compute rates with correct units and counter-reset handling. Show limits as unknown/unlimited when absent rather than inventing percentages. Surface missing expected containers independently of zero usage.

18. **Existing logs.** Add stable request and trace/span correlation through a documented additive log-envelope contract while preserving existing correlation data, redaction, JSONL/stdout, bounded index and runtime-owned ordering. Recompute payload-cap requirements and preserve parser compatibility. An operator must be able to use a trace identity to locate related existing logs. Do not add a second app logger or permit app code to create Privileged audit events.

19. **Probe and inventory contract.** The Host performs protected local readiness checks without exporting its readiness token; the Monitoring server independently probes an uncached public application response with expected content. Keep the runtime health route's opaque unauthorized behavior. Automatic lifecycle synchronization is required in v1. An authenticated inventory interface accepts sanitized expected Host/Capsule identities, lifecycle state and public probe targets from the authoritative Host registry. Bind sender credentials to the exact Host inventory they may update; ingestion authority must not become general monitoring administration. Synchronize initial Host connection and registration, deploy, start, restart, rollback, stop, delete, opt-out and address changes, with periodic background reconciliation that survives workstation disconnection. Use idempotent, versioned per-Host updates, reject stale updates and retain centrally acknowledged expectations independently of sender availability. Explicit stopped/deleted/opted-out state removes active probe expectations; lost contact must never implicitly remove them. Persist pending desired state on the Host and retry after outages without blocking Capsule lifecycle operations. Expose last successful synchronization, pending state and stale inventory. Manual export/import is a recovery tool, not the normal deployment workflow; absence alerts must not rely solely on data from the missing sender.

20. **Export resilience and defaults.** No collector configured means no network exporter or retry loop; normal execution and current logs continue. Reject invalid opted-in configuration clearly before runtime activity. A valid destination's outage cannot block startup, business operations or shutdown. Bound SDK/Collector queues, batch sizes, attributes, retry times, memory and persistent queue disk; shed telemetry with visible loss rather than growing without limit. Flush on shutdown only within a bounded deadline. Automatic recovery retries must not require a workstation.

21. **Sampling and retention.** Start the low-volume canary with full traces for a short measured period and unsampled request metrics. Begin process/infrastructure collection at 15 seconds, metrics retention at 14 days and trace retention at 3 days, with measured disk caps and headroom. Make these operator-configurable. Tune probabilistic trace sampling from measured volume; head sampling does not guarantee all error/slow traces survive. Tail sampling is not required initially. Document capacity from observed rates and sizes, and surface export drops, freshness, queues and backend capacity.

22. **Data minimization.** Use bounded service/Capsule, environment, Host, instance, declared route, method, status and operation metadata. Make release identity available for correlation without unnecessary series multiplication. Trace IDs are not metric labels. Exclude bodies, credentials, cookies, probe tokens, raw queries, SQL parameters, personal identifiers and arbitrary environment/Docker labels by default. Sanitize exceptions before export. Validate incoming trace context, discard unapproved baggage and keep remote sampling flags within operator limits.

23. **Dashboards and alerts.** Provision fleet, Capsule API/traces, resource/runtime and monitoring-pipeline views, including deployment/restart annotations and contextual links. Calculate latency percentiles from independent request histograms. Initial rules: sustained probe failure for 60 seconds; known quota saturation above 90% for five minutes; memory above 85% of known limit for ten minutes or 95% for two minutes; OOM/restart loops; 5xx above 5% over five minutes with at least 100 requests; p95 over a per-route budget for ten minutes with sufficient samples; expected telemetry absent for two minutes; export loss and low disk. Use a one-second initial interactive-route budget and exclude deliberate long streams. Pair near-one-core process pressure with event-loop delay, low traffic or user-visible impact, and allow expected jobs. Quiet services rely on probes/absolute failures instead of noisy percentages. Thresholds are tunable starting policy, not claimed SLOs.

24. **Delivery and diagnostics.** Require a real alert and recovery delivery test in the operator-selected channel. Diagnostic output distinguishes valid configuration, agent state, sender-side DNS/TLS/auth, OTLP acceptance, recent ingestion and stored/queryable data. Explicitly report unavailable verification; a laptop check or accepted HTTP request alone is insufficient. Query verification must not require ingestion tokens to gain unrestricted read privileges.

25. **Rollout and compatibility.** First prove a pinned SDK/exporter in the generated Bundle and exact base image, plus supported Node 22/24 test targets. Then ship stack/agents, connection management, HTTP/runtime instrumentation, deeper operation telemetry and acceptance. Canary the already-repaired `saas-tickets` for 48 hours after isolated drills pass, then enable other Capsules deliberately. Keep source, generated artifacts, public declarations/config contracts, canonical docs and shipped CLI assets aligned. Rebuild generated outputs from source.

26. **Monitoring health.** Expose `GET /health` on the Monitoring server ingress: HTTP 200 with `{"ok":true}` when its telemetry ingestion pipeline and configured metric/trace storage are ready, otherwise HTTP 503 with `{"ok":false}`. Keep checks bounded and the response minimal; do not disclose component addresses, credentials or diagnostic internals. This minimal health route is the exception to authenticated application/admin surfaces and can be called by an ordinary external probe. It is distinct from the existing protected Capsule readiness route, whose authorization remains unchanged. No watchdog, outbound heartbeat, external uptime subscription or dead-man integration is required or shipped in v1. The endpoint alone cannot notify anyone when the Monitoring server is unreachable.

## Testing Decisions

The user confirmed the primary acceptance boundary: **installed Sporades CLI + real generated Capsule + the monitoring Compose stack**, including separate-VM deployment and outages, supplemented by focused redaction and concurrent-context tests.

A good test drives supported operator or application behavior and verifies externally visible outcomes: responses, stored telemetry, retained history, diagnostic envelopes and delivered notifications. Avoid assertions on private helper names, internal call counts or tests that merely restate implementation. Prefer this single end-to-end harness across modes; introduce narrow tests only for properties that cannot be covered efficiently or deterministically there.

1. **Installed package and lifecycle.** Use the packaged CLI to generate the stack and a Capsule, bind a Host and produce real traffic in Dev, Container and Hosted modes. Run the Bundle in the actual base image without installed app dependencies. Verify traces and independent metrics in their storage backends, not only in mocked exporters. Repeat reload/restart/shutdown to prove no duplicate providers or accumulating timers. Prior art: generated server Bundle module-graph tests, packed distribution tests and real-container acceptance tests.
2. **Configuration and Host ownership.** Test local opt-in precedence, automatic coverage of existing and future Capsules on a connected Host, accurate pending-restart reporting, explicit per-Capsule opt-out, Host-disabled policy, invalid settings, registry persistence, credential rotation/revocation and endpoint migration. Disconnect the configuring workstation; restart the Host and redeploy/rollback a Capsule. Verify that existing registry, sealed-key and protected-health contracts remain intact. Prior art: Host-helper lifecycle/registry fixtures and configuration validation tests. Fixtures support focused cases but do not substitute for real-VM acceptance.
3. **Compose and environment contract.** Install on a clean supported VM using the documented `.env`; verify missing-key diagnostics, preserved unknown keys/values, fresh-secret generation, explicit service selection, credential quoting/interpolation and redacted diagnostic output. Upgrade, back up and restore; history, secrets and operator overrides survive. Verify the published package contains its assets and reject unsupported architectures clearly.
4. **Separate-VM topology.** Put Capsules on VM A and monitoring on VM B. Demonstrate outbound-only collection from A, correct private Capsule-to-relay routing, no remote Docker access, trusted TLS and working alerts after A disappears. Interrupt and restore the inter-VM link; rotate/revoke credentials and change the endpoint. Also exercise same-VM setup and document its shared failure domain.
5. **HTTP and trace context.** Drive successful requests, 404, denial, malformed targets, 5xx/translated errors, thrown errors, client abort and streaming completion. Verify correct metrics and exactly one terminal SERVER span, with meaningful children. Overlapping async requests must never cross-parent or cross-correlate their logs. Confirm static health/probe traffic does not dominate traces or hide application failures. Prior art: generated Bundle HTTP/WebSocket behavior tests and endpoint file-response tests.
6. **Dependencies and operations.** Exercise a delayed outbound dependency, SQLite and PostgreSQL work, a WebSocket mutation and a queued/retried job. Verify useful parentage/links and queue metrics while preserving authorization, rollback, at-least-once behavior and restart invariants. Prior art: database adapter conformance, transaction serialization, runtime lifecycle and job inspection suites.
7. **Resource and failure drills.** In a disposable isolated Capsule, run bounded CPU, blocking-loop, heap and Buffer workloads. Confirm the intended CPU/memory/GC graphs, reset handling, OOM/restart evidence and external detection even when the app cannot export. A sustained probe failure must deliver an alert within two minutes in the acceptance environment, followed by a recovery notification. Never induce these failures in the repaired production app.
8. **Pipeline failure.** Stop collectors, disconnect/slow backends, fill bounded queues and restart storage services. Business responses/jobs remain functional; telemetry memory/disk stays within configured bounds; drops and missing data are observable; export recovers and stored history persists. SIGTERM flush cannot outlive its deadline or compromise runtime shutdown.
9. **Expected inventory.** Connect a Host, register, deploy, start, restart, rollback, change addresses where supported, opt out, intentionally stop and delete targets without any manual import/export. Verify automatic synchronization and periodic recovery. Replay or reorder updates, reject cross-Host credentials, interrupt the monitoring connection during lifecycle operations, and restart the sender before reconnecting. Capsule operations remain available, the latest desired inventory eventually arrives, stale updates cannot undo it, and central expectations remain durable when a Host disappears. Intentional lifecycle changes do not page once acknowledged; pending/stale state is visible. Test manual export/import only as recovery.
10. **Privacy and logs.** Seed distinguishable secrets into headers, bodies, queries, exceptions, environment values, SQL parameters and incoming trace metadata. Assert their absence from exported data, new logs, browser artifacts, descriptors and diagnostics. Verify exact request/trace correlation without breaking existing correlation fields, minimum payload caps or index ordering. Prior art: log payload configuration, log index sequencing and credential redaction contracts.
11. **Overhead.** Compare identical representative workloads with telemetry disabled and enabled. Initial gate: no more than 5% p95 latency regression and 5% throughput loss, with a documented measured fixed/load-dependent memory budget and no sustained growth. These are acceptance targets, not current performance claims. Reduce instrumentation/collection overhead before fleet rollout if the gates fail.
12. **Monitoring health.** Verify `GET /health` returns exactly the minimal successful shape when ingestion and configured metric/trace storage are ready, and HTTP 503 with a false result when a required dependency is unavailable. Checks complete within a bounded timeout and disclose no internals. Validate that the stack installs and passes its readiness checks without configuring a watchdog, and that the protected Capsule health route remains protected.
13. **Release evidence.** Pass applicable build/typecheck, generated-source parity, focused behavior tests and real deployment acceptance. Record exact image/package versions, topology, observed retention/disk use, notification delivery and the 48-hour canary outcome. Publishing this specification is not evidence those checks have run.

## Out of Scope

- Reopening or reproducing the fixed `saas-tickets` production incident.
- Browser instrumentation, session replay or Journey capture.
- A new application logger, full centralized log storage/Loki, or replacement of existing audit/index contracts.
- Continuous CPU/heap profiling or claims of precise per-request memory allocation.
- Automatic restart/remediation on CPU thresholds, or resource-quota policy changes beyond limits for the monitoring components themselves.
- Tail sampling in the initial release, Kafka, a second default trace backend, high-availability trace storage and managed SaaS billing integration.
- Multi-tenant hosting of unrelated customers on one monitoring backend.
- Provisioning arbitrary cloud VMs, mandatory SSH administration of the Monitoring server, or a requirement to use a particular LAN, VPN or cloud provider.
- A general-purpose remote monitoring administration/control-plane API beyond the narrowly scoped automatic lifecycle-inventory interface.
- Watchdog integration, outbound dead-man heartbeats and a mandatory external uptime service; v1 provides the simple Monitoring server health endpoint.
- New public plugin/adapter APIs or changes to Capsule authorization, transaction or restart guarantees.

## Further Notes

- This spec synthesizes the agreed monitoring plan, including a self-hostable Compose stack on an independent VM and an available `.env` containing stack secrets. The test boundaries were explicitly confirmed. The subsequent critical-design review confirmed automatic lifecycle synchronization in v1, monitoring enabled for all Capsules on a connected Host with per-Capsule opt-out, local opt-in, and a simple Monitoring server health endpoint without watchdog integration. These decisions supersede the earlier manual-inventory allowance.
- Existing deferred automatic OpenTelemetry planning is the precursor. No matching GitHub OpenTelemetry or monitoring issue was found during the publication check. Keep unrelated historical work open unless separately reconciled.
- Preserve the accepted ADR principles for always-bundled execution, CLI-injected configuration, authoritative Host registry state, Host-owned sealed keys, self-contained deployed Bundles, internal database adapters and runtime-sequenced log indexing. Historical superseded bundler mechanisms must not be reintroduced.
- The operator supplies deployment addresses, TLS material, notification destination and per-route budget overrides during setup; these are installation inputs rather than unresolved product requirements. Default values and validation above make the feature implementable without another design interview.
- Trace-backend scaling or a replacement such as Tempo can be evaluated later through the same OTLP interface if measured volume exceeds the supported single-node envelope.
- Primary references used in planning: [OpenTelemetry HTTP conventions](https://opentelemetry.io/docs/specs/semconv/http/http-spans/), [Collector resilience](https://opentelemetry.io/docs/collector/resiliency/), [Docker stats receiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/dockerstatsreceiver/README.md), [Jaeger Badger storage](https://www.jaegertracing.io/docs/2.21/storage/badger/), and [Prometheus alerting](https://prometheus.io/docs/alerting/latest/overview/). Pin and verify exact implementation versions; reference documentation is not deployed evidence.
