# Atomic Stripe consequences are runtime-owned

A Capsule may declare `stripeEvent({ consequence: "atomic" }, handler)` when one verified Stripe Event must produce one all-or-nothing app consequence. The existing `stripeEvent(handler)` declaration is unchanged: it remains an at-least-once Privileged Job callback that may wait cooperatively on cancellation without holding a database transaction.

The opt-in form is deliberately narrow. The handler receives the userless Privileged identity, the verified Event, app-table access, logging, the Abort signal, Server env, Job enqueue, and one exact-Team read-only `teams.countMembers(teamId)` inspection. The count runs through the existing Privileged Team lifecycle lock on the same transaction adapter and returns only `{ totalCount }`; malformed and absent Team identifiers share `TEAM_NOT_FOUND`. It receives no member identities, directory, Team administration or mutation, payment-provider, mail, File, message, auth-management, Schedule, Access-key, or nested Privileged capability. Context authority is revoked when the callback settles, aborts, or reaches the runtime's 30-second watchdog.

The runtime opens one database transaction, acquires the `stripe-consequence-fence` metadata row before exposing the context or permitting an app read, and holds that fence through commit or rollback. Contending SQLite transactions retry the bounded fence acquisition; libSQL serializes transaction batons; Postgres contends on the same durable row across independent connections. If an adapter reports contention through the complete bounded acquisition window, the runtime durably delays the reserved Stripe Job and returns its claim without spending a provider-delivery attempt. A valid predecessor may therefore use its full watchdog-bounded lifetime without exhausting a follower. Cancellation and claim ownership are rechecked before that deferral. Engine-specific transaction mechanics remain below ADR-0037's adapter seam, while the fence workflow and observable serial history remain shared runtime behavior.

Handler return, pending ACL/log cleanup, and a final Abort check precede commit. A throw, rejected transaction-bound log write, cleanup failure, abort, or watchdog expiry rolls back app writes, transaction-bound logs, and enqueued Jobs. The watchdog revokes the narrow database and Job capabilities before releasing the fence, so a handler Promise that ignores cancellation cannot commit late work. A committed enqueue is dispatched only after commit; a dispatch failure leaves the durable Job available for a later worker. Job claims, retries, lifecycle state, and the single outer `jobs.execute` audit triplet remain outside the app transaction. Failure after the consequence commits but before its reserved Job records success may repeat the attempt, so the handler still owns provider Event idempotency. The transaction makes each attempt atomic; it does not make Stripe delivery exactly once.

This decision adds no general Capsule transaction API and claims no provider-side rollback. Provider I/O stays outside the consequence context because a database rollback cannot reverse it.
