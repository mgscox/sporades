# Access keys are user-owned credential provenance

Sporades needs non-interactive API access without forcing an automation process to own an email address or OAuth login. It also needs Capsule code, ACLs, Files, Teams, Jobs, logs, and operators to distinguish a human Session from named API access without inventing a second authorization model.

An Access key is therefore an immutable, named Credential owned directly by one linked Sporades user. Authentication resolves the current owner into `ctx.auth` and separately exposes `{ kind: "access-key", id, name }` as `ctx.credential`. It does not create a Bot user, Team member, provider identity, actor override, or Capsule-owned credential row. Session work keeps `{ kind: "session" }`. Durable user Jobs capture the admitted user and Credential provenance for attribution while evaluating current Table, File, and Team authority when they execute.

Capsules opt into Bearer admission only with declarative `requireAuth(...)` guards on Custom endpoints or the separate private-File policy. Unwrapped endpoints and every existing Session transport keep their prior behavior. `requireUserAuth(ctx)` is the preferred inline Session/user check; the existing inline `requireAuth(ctx)` name remains a compatible deprecated alias. Missing guard credentials and scopes remain permissive (`["session", "access-key"]` and no required scopes), preserving older Capsules.

The Capsule declares one central concrete scope vocabulary. Keys receive immutable grant expressions, defaulting to `*`; wildcard matching is mechanical, case-sensitive, and evaluated against the current declaration at admission. Scopes narrow only code that explicitly requires them. They never grant row, File, Team, or ownership authority, and Sporades does not infer whether a scope name accurately describes Capsule behavior.

Plaintext is disclosed only by Session-owned issuance or rotation and is never recoverable. The runtime stores a selector plus verifier digest, performs bounded constant-time verification, rejects malformed or dual credentials without downgrade, and freezes the admitted identity/provenance for work already past the credential check. Rotation replaces only the secret. Expiry and revocation affect later admission; password reset, owner unlink, and owner deletion retire current keys atomically. Relinking never revives them.

Owner management is Session-only. Explicit Privileged work and the `sporades access-keys` operator family may inspect bounded metadata and retire exact keys or one exact owner's current keys, but cannot issue, rotate, or receive bearer material. Operator actions run through a live Dev, Container, or Hosted Capsule, use immutable IDs, strict action-specific envelopes, runtime-derived execution source, destructive confirmation, and runtime-owned exact-target audits.

This decision keeps authentication automation additive: existing Capsules need no new declaration, old Session behavior is unchanged, and the same real user remains the authorization actor. The cost is deliberate explicitness. Capsule developers must declare the vocabulary, opt endpoints and Files into Bearer admission, apply the scopes their code needs, and provide any owner-facing management UI. Sporades supplies the credential lifecycle and provenance, not a universal API-key page or a policy inferred from names.
