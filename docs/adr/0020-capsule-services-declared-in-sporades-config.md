# Capsule services are declared in Sporades config

Capsule services are declared as intent in `sporades.json`, while Sporades generates and owns the Docker Compose files under the Runtime directory. Dev sessions start those services before running the Capsule as a local Node process, and local Container sessions run the same services plus the Capsule container on the same Compose network. The first Docker Compose slice should support database Capsule services only, preferably with a database whose SQL dialect stays close to the existing SQLite runtime so Database adapter debugging does not mix orchestration bugs with broad SQL-portability changes. Local Dev sessions and Container sessions share Capsule service data by default so production-like verification uses the same local state; once service volumes exist, reset docs should move away from `rm -rf .sporades` toward explicit reset behavior on the existing Dev, Deploy, and Host command surfaces. The CLI should trend toward common lifecycle verbs such as `status`, `start`, `stop`, and `reset` across `dev`, `deploy`, and `host`, but the Docker Compose slice should only implement the local `dev` and `deploy` pieces it needs. Those verbs can stop services and clean up generated Compose data, networks, volumes, and orphaned resources without introducing a separate `sporades services` command group. The `sporades host` surface already exists; Hosted Capsule service orchestration is the deferred part, and should use the Host command surface later rather than a new top-level namespace. Reset may remove Sporades-owned Capsule images identified by Sporades-generated labels or tags for the current project, but must not remove shared third-party service images such as database images. This keeps service provisioning inside the existing Capsule configuration model, preserves deterministic CLI behavior for agents, and avoids making hand-edited Compose YAML part of the default authoring surface.

The later Database adapter boundary must sit below the existing Sporades authoring API. Capsule code should keep using the stable `ctx.db` table API while the runtime translates that model into engine-specific SQL, connection handling, transactions, schema introspection, and migration behavior.
