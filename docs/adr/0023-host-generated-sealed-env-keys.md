# Host-generated Sealed Server env keys

Hosted Capsule Sealed Server env keys are generated per Hosted Capsule on the Host server. Host private keys stay in Host-owned persistent state; the CLI retrieves only Host public keys and fingerprints, re-encrypts local source values to the Host public key, and pushes only Host-encrypted sealed envelopes.

The Host generates the initial per-Hosted Capsule sealed-env keypair during Hosted Capsule registration, even if the Capsule does not yet use Sealed Server env. Registration therefore establishes the current public key/fingerprint before any release push or local re-encryption command needs it.

The default Host key store is the Host filesystem with strict permissions, because desktop keyrings introduce unlock-password custody problems on headless servers and Docker/system key stores are not portable enough to require by default. Sporades may later support alternative key stores such as systemd credentials, Vault, KMS, or SOPS, but those are optional backends rather than the default contract.

If Host key material is lost, old Host-encrypted envelopes are unrecoverable without the private key. Recovery is re-key and re-seal from the operator's source-of-truth values. Host key backup and restore belongs under a broader Host backup/restore feature, not the first Host-generated keys slice, and Sporades must not provide casual raw private-key export.

The first Host-generated keys slice should support manual per-Hosted Capsule key rotation. Host keys should be addressed by public-key fingerprint, and each release manifest should record the sealed env key fingerprint required by that release's envelope. Rotation generates a new keypair and makes its public key the default for future envelopes, but old keys remain available while retained releases reference them so rollback can decrypt older releases. Key cleanup follows release-retention cleanup and may delete only keys no retained release references.

The Hosted Capsule registry stores the current sealed-env key fingerprint for future re-encryption, while each release manifest stores the sealed-env key fingerprint needed to boot that release. Rollback uses the release manifest fingerprint, not the current registry fingerprint.

The CLI should always re-encrypt to the Hosted Capsule registry's current public key. Fingerprints are generated by the Host from public keys, returned in JSON/status output for audit and diagnosis, stored in release manifests, and used internally by the Host to select the matching private key; they are not routine user input and should not be exposed as a normal `reencrypt` selector.

`sporades host push` should automatically re-encrypt local Sealed Server env values to the Hosted Capsule's current Host public key when local sealed values are available. `sporades env reencrypt --host <alias> --subname <name>` remains available for explicit inspection, CI preparation, and debugging, but normal push should not require a separate preparatory command.

Automatic Host re-encryption must not silently import legacy plaintext `.env.sporades.server` files. If local Sealed Server env is missing but a legacy Server env file exists, `host push` should fail with a clear hint to run `sporades env import` explicitly.

CI/autodeploy env promotion is future work. A CI actor can only produce a Host-encrypted envelope if it has access to source values or decryptable local sealed material, but Host-generated keys do not require Host private keys or plaintext secrets to leave the Host.
