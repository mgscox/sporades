# Settled Stripe Event Job payloads expire after thirty days

The reserved `_sporades.stripe-event` Job necessarily persists the complete frozen Verified Stripe event while delivery remains actionable. A successful Job is settled: its payload and result receive a deadline exactly 30 days after durable `completedAt`. At that deadline the runtime replaces the payload with a non-sensitive marker and clears the result. The terminal Job row, lifecycle metadata, and already-digested idempotency key remain as the replay tombstone, so another delivery of the same provider Event returns the same successful Job and cannot rerun the Capsule consequence.

Queued, delayed, running, failed, and cancelled reserved Jobs are unresolved. Their payload is not age-redacted because doing so would destroy retry or repair evidence. Exhausted and cancelled work therefore remains an explicit operator/privacy exception rather than being falsely presented as settled. An operator must resolve the underlying delivery lifecycle before its normal settled retention clock can apply; this decision adds no generic payload read, delete, or status-rewrite API.

A legacy successful row whose `completedAt` is absent or noncanonical is also unresolved and retains its raw payload without a deadline. Cleanup records the non-sensitive `INVALID_COMPLETED_AT` classification, and operator Job inspection exposes that code with an absent deadline but never the payload or provider identity. There is deliberately no generic Job editor. If a storage recovery or migration restores a canonical `completedAt`, inspection changes to `CANONICAL_REPAIR_PENDING`; the next runtime cleanup reselects the classified row, derives its 30-day deadline, and returns it to normal expiry. Classification compares the exact observed completion value and exact sentinel state, so concurrent repair wins rather than being overwritten. Still-malformed classified rows do not repeatedly re-arm cleanup.

Cleanup is runtime-owned, silent on success, limited to 100 total successful mutations per invocation, and driven at activation, at each new settlement deadline, and after restart. Already-expired deadlines are redacted first; only the remaining shared budget assigns or classifies legacy deadlines, and restart-safe passes drain the rest. Each redaction is an exact compare-and-set on Job identity, successful status, completion time, deadline, absent claim, and absent lease. Concurrent runtimes may select the same row, but only one can redact it, and cleanup cannot cross into pending or newly claimed work. A cleanup failure logs only a bounded runtime code and retries; it never logs Job, provider, Customer, Event, object, payload, or idempotency values.

Thirty days is the platform transport-evidence boundary, not the Capsule's business-record policy. Capsules still own any deliberately selected billing facts, tombstones, export, erasure, and their separately approved retention periods. Raw provider values must not be copied into Capsule tables or logs.
