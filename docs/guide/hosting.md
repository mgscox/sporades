# Hosting Capsules

Hosting has two separate jobs: provision a Host server once, then publish and
operate Capsules on it repeatedly.

For provisioning, follow [Host server installation](../server-installation.md).
For normal Capsule lifecycle commands, use the
[Hosted Capsules reference](../reference/operations-and-hosting.md#hosted-capsules).

The normal publishing sequence is register once, import or seal Server env,
push a release, then verify health and logs. Use structured Host commands so the
same workflow remains operable by people and agents; SSH is an opt-in emergency
compatibility path rather than the management interface.

Validate locally before pushing a release. A Host server is an execution target,
not a substitute for the Dev feedback loop.

For a product's own domain, register one or more exact HTTPS aliases:

```sh
sporades host register fourteen --host personal \
  --alias-domain fourteen.example \
  --alias-domain app.fourteen.example --json
```

Point each domain's DNS at the Host server and allow inbound ports 80 and 443.
For an apex, use A/AAAA records; for a subdomain, use A/AAAA or a CNAME that
resolves to the server. Only attach domains you control. Registration reserves
names on this Host server; it does not change DNS or prove public reachability.
Caddy obtains and renews certificates automatically for each alias. Aliases
use automatic TLS even when the original Hosted domain uses Cloudflare origin
certificates; that domain's wildcard certificate is not reused for aliases.

The original subdomain keeps working and remains the canonical `hostedUrl`.
Aliases share the Capsule's container, data, logs, and unavailable response.
They survive push, restart, rollback, and stop; unregister removes all routes.
`host list --json` exposes the authoritative `aliasDomains` list. The local
binding and `remoteCapsuleId` remain unchanged.

Choose one registered alias as the public origin for links generated by the
Capsule. Registration can select it immediately with
`sporades host register fourteen --canonical-domain app.fourteen.example`; the
name is automatically included among the routed aliases. For an existing
Capsule, `sporades host canonical set fourteen app.fourteen.example` selects an
alias already registered to that Capsule, and
`sporades host canonical clear fourteen` restores its Host subdomain as the
public origin. Both operations restart a running Capsule so it sees the new
origin; a stopped Capsule stays stopped. The Host subdomain continues serving
the Capsule, and requests are not redirected. These commands change routing
metadata only: they do not provision DNS or alter `hostedUrl` or the Capsule's
identity.

If a canonical change is interrupted or its restart fails, retry the same
command after repair to apply the saved origin. A successful `host start` also
applies it. An explicit `host stop` cancels the pending restart, so later
canonical commands keep that Capsule stopped.

Aliases are selected at registration (up to 20, lowercase ASCII/punycode DNS
names). To change an existing Capsule's aliases, unregister it, then register
it with the complete replacement list and start it again. This causes downtime
but retains its data and releases. Re-registering without alias flags retains
the previous list, subject to fresh ownership checks. An unregistered Capsule
no longer reserves its aliases, so another Capsule can claim them. The helper's
low-level registration request accepts `aliasDomains: []` to clear the list.

Upgrade the Host helper and rebuild/push the Capsule with this version before
using custom-domain browser requests. The CLI requires the helper to confirm
all explicitly requested aliases before writing a local binding. If an older
helper ignores them, registration reports an error: upgrade the helper and
inspect the remote registration before retrying, since the canonical Capsule
may already exist even though alias ownership is unconfirmed.
The runtime admits only registered
HTTPS aliases, and OAuth requires matching host, origin, and forwarded headers.
Configure each alias callback URL with your OAuth provider and update any
explicit payment/public-origin settings in the Capsule. Built-in password-reset and Team Join links use `ctx.app.publicOrigin`, including
the canonical alias when configured. Cookies remain
scoped to each hostname; sessions are not shared between domains.

If registration and its rollback both fail, the helper keeps a durable hostname
reservation under `registry/registration-claims/` and reports both the original
failure and any route/runtime recovery failures. Repair Caddy or the Host
storage problem, then retry the original registration. Omitted alias flags
reuse the pending registration's alias list; changing that list is rejected
until recovery completes. Successful retry commits the registry and removes
the pending reservation. Other Capsules cannot claim those names meanwhile.
A registry lock cleanup failure after commit preserves the committed route and
reservation. Repair the reported lock cleanup problem, then retry registration
to complete recovery. Unregister and delete reject Capsules with pending
registration recovery; complete that recovery first, then tear down normally.

## Publish a new Capsule: verification points

The sequence is register, seal Server env, push, then verify. Several of those
steps report success while the thing they configure is not actually working, so
check each one by behaviour.

### Verify DNS away from the development machine

A dev box behind a VPN resolver, an exit node or an HTTP proxy can hold a stale
negative answer for a record that is published correctly. The local resolver
returns nothing, `curl` reports a 502 from the proxy or an SSL `unexpected eof`,
and the zone looks broken when it is not. Query a public resolver directly and
fetch the site with the address pinned:

```sh
curl -s -H "accept: application/dns-json" \
  "https://cloudflare-dns.com/dns-query?name=app.example&type=A"
curl -s --resolve app.example:443:EDGE_IP https://app.example/ -o /dev/null -w "%{http_code}"
```

Unset any `*_PROXY` variables for the second call. If those two succeed, the
site is live and only the local resolver is wrong.

### Read the boot log before declaring mail or support ready

A release declares the Server env keys it requires. If any are missing the
container logs `env.required.missing` and names them exactly; the app then boots
with that feature silently unavailable. Key names are not guessable — a
plausible `SMTP2GO_USERNAME` is not the key, and the runtime wants
`SMTP2GO_SMTP_USERNAME` — so push, then read:

```sh
docker logs CAPSULE_CONTAINER 2>&1 | grep env.required.missing
```

`sporades env export` produces a transfer artifact under the project keypair; it
installs nothing. Prove a secret is live by behaviour — a delivered message, an
accepted event — not by the export command exiting 0.

### Opt in to observability in `sporades.json`

Error reporting is a top-level `observability` key in `sporades.json`:

```json
{ "observability": { "errors": { "protocol": "sentry", "dsnEnv": "ERROR_DSN", "client": true } } }
```

The same key in `app.config.json` is accepted and ignored, and
`sporades host services connect SUBNAME` then answers `project-not-opted-in`
with no further explanation. Place `connect` with the subname and no flags; it
creates the project, seals the DSN and asks for a push. Creating the project by
hand first leaves a duplicate that the API key may not be allowed to delete.

Sealed DSNs do not appear in `docker inspect` or `printenv`. Read the
`observability` block from the capsule's `current/sporades.json`, then prove the
DSN with a synthetic store POST.

### Analytics needs the script tag in the app

`connect` seals the error DSN only. The template ships the analytics script
element commented out in `index.html`; publish it with the dashboard URL and the
website id, or the page loads with no measurement at all:

```html
<script defer nonce="%SPORADES_NONCE%" src="https://analytics.example/script.js" data-website-id="WEBSITE_ID"></script>
```

### Prefer the provider API to the panel

Both mail providers can be configured without a browser, which keeps the steps
repeatable and auditable.

MXroute's REST API is `https://api.mxroute.com/` — no version prefix — and every
request carries `X-API-Key`, `X-Server` and `X-Username`. Adding a domain needs
proof of ownership first: `GET /verification-key` returns a `_da-verify-<hash>`
name and the value `domain-verified` to publish as a TXT, and only then does
`POST /domains` accept the domain. `GET /domains/<domain>/dns` returns the
records to publish. Its DKIM value arrives with literal double quotes around
it — strip them before writing the record, or verification fails with the record
present and correct-looking. Create mailboxes with
`POST /domains/<domain>/email-accounts`.

SMTP2GO uses `/v3/` endpoints with the key in the JSON body: `domain/add`
returns the per-domain DKIM and return-path names, `domain/verify` reports
`dkim_verified` and `rpath_verified`, and `users/smtp/add` creates the sending
user. Response envelopes differ between endpoints, so re-list rather than trust
a create response.

Finish mail setup with a real round trip: authenticate SMTP over TLS, send from
the new mailbox to itself, read it back over IMAP, then delete the test message.

### Check the product key against the code

`billing.products.<key>` accepts any key, but authorisation code and client
handlers often compare against one literal (`productKey !== "pro"`). A config
key that does not match renders a correct pricing page and refuses every
checkout with no configuration error. Grep `server/` and `client/` for the
literal before binding Stripe IDs.

Placeholder legal values are also a gate: a `legal` block that still reads
"Replace with entity name" keeps billing dormant however complete the Stripe
wiring is, because a buyer must be able to identify who they contracted with.

## Read a Hosted Capsule's database

`sporades host db list|dump|query` runs the same read-only inspection as
`sporades db` against a running Hosted Capsule, over your existing SSH access:

```sh
sporades host db query "select count(*) as total from todos" --subname fourteen --json
```

The JSON matches `sporades db query --json`, so a pull script can target a Dev
session or a Hosted Capsule by changing only the command. Upgrade the Host
helper and redeploy the Capsule with this CLI first. See
[Hosted Capsule database](../reference/operations-and-hosting.md#hosted-capsule-database).

## Capsule data backups

Configure opt-in encrypted local or S3 backups with `sporades host backup configure`.
See [Capsule backups and restore rehearsals](../reference/capsule-backups.md) for
create/list/restore/prune, the Host timer, retention and stale-backup alerts.
